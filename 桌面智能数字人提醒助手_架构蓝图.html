桌面智能数字人提醒助手：项目开发架构与蓝图

文档版本：v1.0
生成日期：2026-05-23
目标平台：macOS 桌面端优先，后续扩展 Windows / iOS / Android
项目定位：一个常驻用户桌面的智能数字人生活时间管理助手，帮助用户管理闹钟、重要日程、会议、待取快递、演唱会门票开抢、生活缴费、课程、出行等“时间卡点”事项。

1. 项目愿景

用户每天会面对大量与时间相关但分散在不同 App、短信、日历、聊天消息、邮件和网页中的生活事项，例如：

  • 明天早上 7:30 起床闹钟
  • 上午 10:00 线上会议
  • 下午 15:00 去取快递
  • 晚上 20:00 演唱会门票开抢
  • 周五 14:00 体检预约
  • 周末高铁出行提醒
  • 水电燃气缴费截止日
  • 朋友生日、纪念日、课程、考试、面试

本项目希望通过一个“桌面智能数字人”把这些事项统一抽取、理解、管理和提醒。它不是简单的闹钟软件，而是一个具备自然语言理解、工具调用、事件编排和多通道提醒能力的个人生活智能体。

2. Harness Engineering 概念说明

2.1 推荐中文翻译

Harness Engineering 在本项目中建议翻译为：

智能体运行框架工程

也可以在文档中补充说明为：

围绕大模型构建一套可控、可观测、可恢复、可扩展的智能体执行框架，而不是只依赖 Prompt 本身。

2.2 在 AI Agent 中的含义

在传统软件工程中，harness 常见于：

  • test harness：测试运行框架
  • evaluation harness：评测框架
  • agent harness：智能体运行框架

在智能体产品中，Harness Engineering 强调：

  1. 模型不是完整产品：LLM 负责理解、推理和生成，但真正让产品可靠运行的是模型外部的执行系统。
  2. 工具调用需要被编排：日历、提醒、快递、邮件、网页、票务信息、系统通知等都需要统一接入。
  3. 状态必须可管理：提醒是否创建、是否触发、是否确认、是否失败重试，都需要被记录。
  4. 安全边界必须清晰：抢票、付款、删除日程、发送消息等高风险动作必须有人类确认。
  5. 结果需要可评测：系统要能评估提醒是否准时、识别是否准确、误报漏报率如何。
  6. 失败要可恢复：网络失败、API 失败、模型误判、系统休眠等场景都要有补偿机制。

2.3 本项目中的 Harness Engineering 定义

本项目采用 Harness Engineering 作为核心架构思想：

通过数字人交互层、任务理解层、工具编排层、提醒调度层、记忆与上下文层、权限与安全层、观测与评测层组成一个完整智能体运行框架，使数字人能够可靠地帮助用户管理日常生活中的关键时间节点。

3. 产品目标

3.1 核心目标

  1. 统一管理生活时间事项：闹钟、会议、日程、快递、门票开抢、缴费截止、出行、生日纪念日等。
  2. 自然语言创建提醒：用户可以说“明晚八点提醒我抢周杰伦演唱会门票”。
  3. 桌面常驻数字人提醒：通过桌面数字人形象、气泡、语音、系统通知进行提醒。
  4. 多级提醒策略：提前一天、提前一小时、提前十分钟、准点提醒、超时补提醒。
  5. 重要事项确认闭环：提醒后需要用户确认“已处理 / 稍后提醒 / 忽略”。
  6. 支持外部信息接入：日历、邮件、短信、快递、票务网页、聊天记录等。
  7. 可扩展智能体框架：后续可接入更多工具和平台。

3.2 非目标

MVP 阶段暂不直接实现自动付款、自动下单、自动抢票等高风险行为。系统可以提醒用户打开对应页面，但真正购买、支付、提交订单应由用户确认完成。

4. 用户场景

场景 1：自然语言添加提醒

用户输入：

明天早上 8 点提醒我开部门晨会，提前 10 分钟再提醒一次。

系统行为：

  1. LLM 解析意图：创建会议提醒。
  2. 提取时间：明天 08:00。
  3. 提取提前提醒：提前 10 分钟。
  4. 写入提醒数据库。
  5. 桌面数字人反馈：“好呀，我会在明天 7:50 和 8:00 提醒你。”

场景 2：演唱会门票开抢提醒

用户输入：

5 月 30 日晚上 8 点周杰伦演唱会开票，提前半小时提醒我。

系统行为：

  1. 创建票务类型提醒。
  2. 设置提前 30 分钟提醒和准点强提醒。
  3. 可附加购票链接。
  4. 到点时弹出桌面提醒、语音播报，并显示“一键打开购票页面”。

场景 3：快递待取提醒

系统从快递短信或用户手动输入中识别：

顺丰快递已到菜鸟驿站，请凭取件码 1234 取件。

系统行为：

  1. 提取快递公司、取件地点、取件码。
  2. 创建“待取快递”任务。
  3. 根据用户常用取件时间推荐提醒，例如下班后 18:30。
  4. 若用户未确认已取件，次日继续提醒。

场景 4：会议提醒

系统接入日历后识别会议：

  • 会议时间：10:00
  • 地点：腾讯会议
  • 链接：会议 URL

系统行为：

  1. 提前 15 分钟提醒准备。
  2. 准点提醒并展示会议链接。
  3. 用户点击“打开会议”。
  4. 会议结束后可询问是否记录纪要。

6. 分层架构设计

6.1 桌面数字人交互层

职责：

  • 展示桌面数字人形象
  • 支持文字对话
  • 支持语音输入与语音播报
  • 显示提醒气泡
  • 显示系统通知
  • 支持快捷操作按钮，例如“稍后提醒”“已完成”“打开链接”

推荐技术：

  • MVP：Python + PySide6 / PyQt6
  • 可选：Electron + React + Live2D / Spine / Rive
  • macOS 通知：NSUserNotification / pync / terminal-notifier
  • TTS：Edge TTS / OpenAI TTS / 系统语音
  • STT：Whisper / faster-whisper / 系统语音识别

6.2 智能体运行框架层

这是 Harness Engineering 的核心。

核心模块：

  1. Intent Router 意图路由器

  2. 判断用户是在创建提醒、查询日程、修改闹钟、记录快递、设置票务提醒，还是普通聊天。

  3. Task Planner 任务规划器

  4. 将复杂请求拆成步骤。

  5. 例如：“帮我查一下周五上海天气，如果下雨就提醒我带伞”会拆为天气查询、条件判断、提醒创建。

  6. Tool Orchestrator 工具编排器

  7. 统一调用日历、数据库、系统通知、浏览器、快递查询、票务页面等工具。

  8. State Manager 状态管理器

  9. 管理提醒状态：pending、scheduled、triggered、acknowledged、snoozed、expired、cancelled。

  10. Memory Manager 记忆管理器

  11. 存储用户偏好：常用起床时间、通勤时间、常用快递点、喜欢提前多久提醒、重要联系人等。

  12. Permission Guard 权限守卫

  13. 高风险操作必须确认：删除大量提醒、打开外部链接、自动提交表单、购票、支付、发送消息。

  14. Failure Recovery 失败恢复器

  15. 网络失败重试。
  16. 系统休眠后补提醒。

  17. 模型解析失败时追问用户。

  18. Evaluation Harness 评测框架

  19. 统计提醒准时率、用户确认率、误报率、漏报率、解析准确率。

6.3 业务服务层

核心服务：

  • Reminder Service：通用提醒服务
  • Alarm Service：闹钟服务
  • Calendar Service：日程与会议服务
  • Parcel Service：快递待取服务
  • Ticket Reminder Service：演唱会/活动门票开抢提醒服务
  • Notification Service：通知编排服务
  • Preference Service：用户偏好服务
  • Search Service：事项搜索服务
  • Sync Service：外部数据同步服务

6.4 数据与状态层

MVP 建议使用：

  • SQLite：本地桌面数据存储
  • SQLAlchemy：ORM
  • Alembic：数据库迁移
  • Chroma / SQLite FTS：本地语义搜索或全文搜索

正式版本可升级为：

  • PostgreSQL
  • Redis
  • Qdrant / Milvus / pgvector
  • Kafka / RabbitMQ

6.5 外部工具与集成层

可接入：

  • Apple Calendar / Google Calendar
  • Gmail / Outlook
  • 短信和邮件解析
  • 快递查询 API
  • 票务网站链接监控
  • 浏览器自动打开页面
  • macOS 系统通知
  • 微信/飞书/Telegram 通知

8. 核心模块设计

8.1 提醒模型

class Reminder:
    id: str
    user_id: str
    title: str
    description: str | None
    category: str  # alarm, meeting, parcel, ticket, travel, bill, custom
    start_time: datetime
    timezone: str
    remind_offsets: list[int]  # 例如 [-1440, -60, -10, 0]
    priority: str  # low, normal, high, critical
    status: str  # pending, scheduled, triggered, acknowledged, snoozed, cancelled
    source: str  # manual, calendar, email, sms, browser, llm
    action_url: str | None
    metadata: dict
    created_at: datetime
    updated_at: datetime

class ParcelTask:

    tracking_no: str | None
    pickup_code: str | None

    reminder_id: str | None
    raw_text: str | None

class TicketEvent:

10. 智能体执行流程

10.1 创建提醒流程

用户输入自然语言
    ↓
Intent Router 判断为 create_reminder
    ↓
LLM 结构化抽取：标题、时间、类型、提前提醒、优先级
    ↓
时间解析与歧义检查
    ↓
权限判断：普通提醒无需确认，高风险动作需要确认
    ↓
写入 Reminder 数据库
    ↓
Scheduler 注册定时任务
    ↓
数字人反馈创建成功

10.2 到点提醒流程

Scheduler 到点触发
    ↓
读取 Reminder 状态
    ↓
Notification Service 编排提醒
    ↓
桌面弹窗 + 数字人气泡 + 语音播报
    ↓
用户选择：已完成 / 稍后提醒 / 忽略 / 打开链接
    ↓
更新状态并写入事件日志

10.3 系统休眠恢复流程

系统唤醒
    ↓
扫描过去未触发的 reminder_instances
    ↓
判断是否仍需补提醒
    ↓
对 critical/high 级事项立即补提醒
    ↓
记录 missed_trigger 事件

13. 安全与隐私设计

  1. 默认本地优先，用户数据存储在本机。
  2. API Key 存储在本地 .env 或系统 Keychain。
  3. 高风险动作必须用户确认。
  4. 外部链接打开前显示来源和风险提示。
  5. 不自动执行购买、支付、提交订单。
  6. 支持导出和删除个人数据。
  7. 日志中不得记录完整敏感内容，例如取件码、身份证、手机号、票务账号密码。

  • 高优先级提醒完成率
  • 用户手动修改提醒比例
  • 快递提醒完成率
  • 票务提醒点击率

14.3 评测数据集

建立固定测试用例，例如：

明天早上七点叫我起床
下周三下午三点提醒我开会
今晚八点提醒我抢演唱会票
顺丰快递到了，取件码 1234，晚上提醒我取
每周一早上九点提醒我写周报

评测字段：

  • 意图是否正确
  • 时间是否正确
  • 提醒类型是否正确
  • 提前提醒是否正确
  • 是否触发必要追问

15. 风险与应对

风险 应对
LLM 时间解析错误 使用结构化输出 + 时间解析库 + 用户确认
系统休眠导致错过提醒 唤醒后扫描补提醒
通知被系统静音 重要事项多通道提醒
用户隐私泄露 本地优先、敏感字段脱敏
第三方 API 不稳定 缓存、重试、降级
误触发高风险动作 权限守卫、人类确认

17. 结论

本项目的关键不是做一个普通闹钟，而是做一个以 Harness Engineering 为核心的桌面生活智能体。大模型负责理解用户意图，智能体运行框架负责把意图变成可靠、可追踪、可恢复的真实行动。通过桌面数字人的拟人化交互，用户可以用更自然、更低压力的方式管理生活中所有关键时间节点。

推荐从 MVP 开始：

  1. 先做好本地提醒和调度闭环。
  2. 再接入 LLM 做自然语言创建提醒。
  3. 然后扩展快递、会议、票务等高频生活场景。
  4. 最后再考虑多端同步和复杂自动化能力。
